# Pi 1.0.0 与当前实现及建设合同兼容性审计

**日期：** 2026-10-03  
**基线：** 主仓 `main`，审计时 HEAD `6a80920`；Pi `0.87.1`、pi-subagents `0.71.0`。  
**结论：** **NO-GO，尚不允许切换生产。** 静态 API 大部分兼容，但原生 ESM 同实例合同已证失败；新工具调用面必须明确收紧；未来建设范围不能由历史文档自动恢复。

本报告覆盖仓内当前生产实现、全部计划目录的状态盘点，以及可识别的未来建设合同。它不声称已审计未提供源码的仓外项目，也不声称已完成纯净 1.0.0 依赖闭包、真实模型和完整生产 canary。缺失范围明确列为门禁，而不是“默认兼容”。升级实施计划见 `docs/plans/2026-10-03-pi-1.0.0-compatibility-upgrade.md`。

### 2.1 Goal 冲突的处理

`9b9cbb8` 已是主线祖先，明确移除主线 Goal，转入独立功能分支。当前无 `src/goal-engine/`、`pi/extensions/goal-engine.ts`、真实 Goal canary 或 Goal npm script。历史 summary 的 GREEN 不能代替当前 R13。

仍有效的根 AGENTS 门禁：R0–R13 全部完成且 R13 通过前，禁止 Goal Engine 执行、编排、验收其改造；冻结 planned-goal 不阻塞 R1–R13。旧 spec 中“先完成 planned-goal”的相反要求不得执行。

旧 R0–R13 的 `scripts/lib/**/*.mjs` WritePaths 与当前 feature-owned `.ts` 规则冲突；恢复时须重写路径/接口计划，不能直接照旧执行。升级计划不修改历史 generation，不恢复 auto-continuation，不把 Pi Durable 当替代 authority。

### 2.2 生命周期不应被宣称已完成的项

- `durable-run-registry.ts`、`supervisor-replay.ts` 缺 production importer。
- lifecycle identity/policy 的组件存在不等于已接入生产 expiry/recovery。
- scheduler `recoverySource` 只有可选注入，当前无生产 provider。
- `L-REGISTRY-ENTRY` 为 blocked-unknown：Inventory 引用要求 `{id,digest,revision,reference}`，public workspace receipt 缺后三项；OwnerReceipt 的转换规范未冻结；不能手工剥 digest 前缀或读私有 ledger 合成引用。
- control plane 并发 resolve→native→commit 缺独立 claim；旧 receipt 与新 pending 优先级待产品裁决。
- ended-child 自动 resume 已正式退役；保留 durable intent、queue/proof/owner 检查和 main-agent handoff。普通 resume、heartbeat 不退役。

升级保护这些边界，但不强制在升级中建设全部后继组件。是否收缩合同或继续建设，必须有独立决策。

## 4. 同实例阻塞与修复候选

合法生成链：

```text
init-pi.sh → setup-subagent-runtime-deps.ts
→ npm install --ignore-scripts --omit=peer（没有omit dev）
→ enhanced dev四包落盘
→ subagent-runtime → compat/pi-subagents-0.71.ts
→ pi-subagents root → native extension/index.js
→ watchdog/register-main.js → watchdog/render.js
→ enhanced physical pi-tui → new Container
```

首个偏离点是把 jiti 的 TS mapping 当成 Node native ESM mapping。已证实际 renderer 的 constructor `=== enhanced` 且 `!== Host`。当前双方版本同为0.87.1；1.0候选也未解决。可render不等于同实例合同成立，具体crash仍未证。

候选比较：

1. **unbundled parent native resolver**：原理探针使0.87 watchdog等于Host；不得挪用 child marker 作为生产parent开关。需独立入口、解析范围和完整unbundled闭包；不能当bundled默认解法。
2. **embedded namespace bridge**：TS factory捕获实际Host namespace，native resolver仅把受限specifier映射至导出相同对象的bridge；1.0 bundled探针四对象与实际watchdog相等，dev typings保留。尚需Node22.19、load/reload/cache/generation、注册失败回滚和跨feature范围测试。
3. **absolute child SDK import**：上游 `child-session.js` 通过绝对 export entry import SDK，bare bridge不覆盖；公开composition注入是否可达未证，必须独立门禁。

已否定作为默认修复：删除四local包、只改peer声明、只jiti alias/tryNative:false、只指全局physical包、同步转译上游async bootstrap。不得放宽Doctor换取绿色。

**发布停止条件：** 若无法通过公开可维护的composition覆盖所有运行加载边界，输出NO-GO并保留证据；不vendor Host、不深import上游内部、不扩大万能resolver。允许提出上游修复建议，但提工单须用户确认。

## 5. 新工具权限、扫描、取消与模型边界

### 5.1 精确默认与权限边界

- CLI默认加载 `builtin:mcp`、`builtin:llama.cpp`、`builtin:codemode`、`builtin:tool-search`。
- `codemode/tool_search` 默认inactive，不代表未注册；MCP配置可自动激活。
- `autoEnableCodemode:false` 在mcp.json顶层，只阻自动激活，不禁连接/其他nested调用。
- MCP hidden仍可连接；`enabled:false`或不加载MCP才避免连接。
- exposure默认direct；active direct可直接与nested调用。
- model-only允许直接模型调用、拒绝nested；hidden不可达。
- codemode/deferred可在inactive时callable；`setActiveTools`和hiddenDeclarations不是权限边界。
- CLI `--tools` / SDK `tools` 是registry硬ceiling；`--exclude-tools`是精确名称，不是glob。
- settings `extensions:["-builtin:mcp",…]`有用，但项目`+builtin:*`/显式`-e`可覆盖；安全入口必须同时审计trust、explicit entries及child继承。
- `--no-extensions`仍允许显式`-e`。若使用此模式，必须显式加载安全门禁/typed入口，不能把“所有扩展禁用”当仍有安全膜。

**建议此次产品基线：** core升级不开放MCP/codemode/tool_search/virtual/image/classifier新能力；禁用新增built-ins并对人工/child入口建立可验registry ceiling；typed orchestration、workspace、supervisor及scheduler交互工具用model-only。此建议须在升级计划批准时明确，不把它当用户已做出的历史决策。

### 5.2 结果与取消

`src/security-gates/extension.ts`当前提醒hook只返回content/details/isError。1.0 content替换但不返回structuredContent会删除structure；这是防止结构与改写文本不一致的设计，不是偶发损坏。不能盲目spread未经扫描的原结构。目前行为是coding reminder，不是通用redaction器：仅在真实合法本地工具生成结构、同等审计与语义一致均已证明时同步保留；否则保持删除行为并记录consumer限制。测试手工制造新结构不构成production兼容依据，未来MCP需要独立双通道政策。

`ctx.executeTool()`返回outcome，工具失败不必reject，调用者必须检查isError。MCP有outputSchema时codemode可能先返回结构，不能把Promise resolve或结构存在当成功。

nested记录在父result的bounded `nestedCalls`，非独立session toolResult：256call、单项8KiB参数、总32KiB、无完整results，complete:false可表示截断/未完。**记录上限不是执行预算，也不是完整扫描authority。**

取消信号只在未开始时可靠阻止执行，已接收副作用不回滚；current subagent/workspace/scheduler部分execute忽略signal。script超时、Rpc abort或nested failure不等于owned terminal proof。Goal R8未来仍要求durable suspend/revoke→typed stop→proof/quarantine。

### 5.3 模型

virtual selection与physical response model分离；当前providerBlacklist验证selection，不足以约束physical。默认安装不会凭空创建router，但trusted extension注册可加入catalog。建议typed范围暂拒`api:"pi-virtual"`，保留普通chat与现有fallback；未来启用需每request physical policy、child注册传播、actual model/context/cost证据。

codemode的4并发是每script模型调用限制，不是总费用/次数预算；默认script timeout无限。Tool hooks不覆盖images/classifier模型调用，不能把工具ceiling当模型成本门禁。

## 7. 成本与实施范围决策

浅层core估算3–6人日不足以覆盖本轮完整审计揭示的加载阻塞。建议采用以下条件式估算：

- 现有产品能力的隔离升级与完整回归：**5–9人日**。
- 同实例边界产品化与absolute SDK路径探索：**额外2–5人日**，可能得出NO-GO；不承诺一定可修。
- 新MCP/codemode/virtual正式启用：**另立范围，额外2–5人日起**，需政策/扫描/预算/真实endpoint证据。
