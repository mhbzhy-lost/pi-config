## 真实入口、事实与顺序

| 环节 | 现场源码 | 能获得什么 / 不能得到什么 |
|---|---|---|
| Host 启动 | `packages/pi-subagents-enhanced/extensions/subagent-runtime.ts` 的 `subagentRuntime` → `installHeadlessTypedSubagentRuntime({beforeUpstreamSessionStart})`，`src/subagent-dispatch/extension.ts` 的 `beforeSessionStart` 先调用此前置，再启用订阅 | `stateRoot` 存在时构造私有 `AuthorityStore`，并注入 `RootBrokerServer`；缺失时 store 为 `undefined`，仍可启动 legacy broker；`connectRuntimeCoordinator` 可能返回 `undefined`。启动不是某次 run 已授权/拥有 workspace 的证明。 |
| child 身份与授权 | `src/subagent-dispatch/extension.ts` 的 `executeCoding/executeGeneric`：`ensureAllocated` 在 spawn 前；`onBinding` 取得 upstream 观察的 run binding，**仅有 workspace 时** `registerAuthorizedRun(codingRunAuthorization/genericRunAuthorization)`；随后等待 registration，再 `workspaceService.bindRun({workspaceId,run:binding})`。Host 回调在 `extensions/subagent-runtime.ts` 的 `registerAuthorizedRun: async (authorization) => ...registerRootBrokerAuthorizedRun(...)`。恢复链为 `connectRuntimeCoordinator` 注入 `createRecoveryResumeOrchestrator` → `rpc.resume` → `subagent:async-started` 身份验证 → `registerAuthorizedRun` → `client.activateResume`。 | Host 回调入口有原始 `RunAuthorization`，但 Promise 返回 `void`，且发生在 workspace **bindRun 之前**；恢复链的 `activateResume` 在授权之后。不能把 preallocate receipt 当已绑定该 run 的 receipt。 |
| Root authority commit | `root-broker-server.ts` 的 `registerAuthorizedRun(authorization: Readonly<RunAuthorization>): Promise<void>` 先校验 binding/session/capabilities。`capabilities.length===0` 只登记 facade 并返回；否则观察 OS processBirth，`identityState=verified` 且有 `authorityStore` 才 `createOwnerReceipt`、`authorityStore.createWithLease`，之后成功完成 principal 登记。`readOwnerReceipt(runId): Promise<OwnerReceiptV1>` 经 Store 检查非 revoked/superseded；`AuthorityStore.readLease(runId)` 可读 durable lease，但当前 Host 不为 inventory 调用。 | 对有能力且 Store 可用的 coding run，授权完成后可再读取 OwnerReceipt 和 Lease；不能从注册 `void`、内存 ownedRuns、supervisorControlPlane 的 catch→`undefined` 推断 owner/lease。`generic` 的 `capabilitiesForRun` 为 `[]`，即使有 workspace 也不会创建 OwnerReceipt/lease。无 Store / processBirth 未证实 / stale 或 unavailable 时必须阻止 inventory（`root-broker-server.ts` 明言 in-memory 不能合成 receipt；`authority-store.ts` 读失败会 fail closed）。 |
| workspace / provenance | `workspace/service.ts` 的 `v2Receipt` 返回 `schemaVersion/workspaceId/leaseId/owner/.../state/run/...`，`bindRun` 才把 run 写入 ledger 并返回 receipt；`listOwned` 经 public service 可按 ownerScope/runId 读。`durable-contract.ts` 的 `InventoryReferenceV1` 必需 `{id,digest,revision,reference}`，其中 digest 为**无前缀**的 64 位小写 hex；`ProvenanceV1` 要求分类及真实 `observedAt`，`unconfirmed` 还需要合法 quarantineReference。 | v2 public receipt **没有** `revision/digest/reference`，也未见相应受信 reference adapter；`authority-contract.ts` 的 `parseWorkspaceReference` 要求另一套 `{schemaVersion,workspaceId,leaseId,revision,digest,reference}`，service 的 v2 receipt 本身不符合。不得从 ledger 私有 revision、workspaceId、leaseId 或手工 hash 合成四元组。`RunAuthorization` 只有 binding/goal/capabilities；OwnerReceipt 的 `digest` 和 `authorizationReference` 是 `sha256:` 前缀，OwnerReceipt 没有现成的 `{id,digest,revision,reference}` 转换规范；authorizationReference 本身无独立 receipt id/revision。当前 Host 也没有针对 inventory 的权威分类、采集时点、quarantine provenance provider。 |
| 持久化 | `durable-run-registry.ts` 的 `recordInventory(value: unknown)` 精确校验 `runId`、三份四元引用、provenance 后以 `DurableStorage.write` revision CAS 持久化；`durable-storage.ts` 创建私有 root、锁和 fsync。 | 解析/锁/CAS 只保证写入形式，不证明引用来源、run/workspace/owner 的身份相等和时间顺序。测试中的固定 `production` 时间与相同 `a` digest 是测试制造数据，不是合法生产记录。 |

**合法写入时点（条件式）**：只在受信 Host 已捕获 `subagent:async-started` binding、Broker 成功 durable commit OwnerReceipt+Lease 并能回读未撤销且匹配的 current generation、public `managed-workspace.v2` service 已返回绑定同 run 的 receipt（或经合法 resume/rebind 返回的等价 receipt）、且可信 provenance 和三份四元 reference 均可验证时；写入在依赖 recovery/replay inventory 之前完成，失败必须返回 blocked/debt 并保留事实，不得把 registry 写成功视为新的 authority。现有分散于 `src/subagent-dispatch/extension.ts`（binding/receipt）与 Host `extensions/subagent-runtime.ts`（Broker/store）的回调，尚没有一个同时取得这些值并负责顺序的生产接口。对于无 managed workspace 的 run，还需明确是否 inventory 不适用或有权威空 workspace 表示；`InventoryV1.workspaceReference` 为必需字段，不能伪造空对象。`recoverOrphanRun` 在 `recovery-resume-orchestrator.ts` 只是注入式 gate/opaque `ownerReceiptId` 和可选 lease expiry，未组合 registry 或提供四元引用；它不是补全缺失输入的捷径。

## 后继合同：先取证，再冻结 WritePaths/RED/GREEN

**当前不能给出可直接 coding 的最小 GREEN**。所缺权威契约：

1. 生产 `RunAuthorization` 的独立、可校验 `{id,digest,revision,reference}` 来源；OwnerReceipt（其 digest 为 `sha256:` 前缀）和其当前 generation/lease 的授权转引用规范与关系验证；严禁把字符串剥前缀当成已获授权的 reference。
2. `managed-workspace.v2` public service 返回的精确四元引用或其由 workspace owner 明确发布的 public adapter，证明 revision/digest/reference 对应 bindRun/rebind 后的同一 receipt。须说明 workspace 可选时 inventory 契约怎样处理，不能读取私有 ledger 或合成 token。
3. Host provenance 的真实观察事件、时点与分类权威、unconfirmed quarantineReference 来源；以及生产 `recordInventory` 私有 root、错误/重试/顺序协议和恢复匹配约束。

**定位到的最窄既有组合路径与签名（仅设计候选，未获字段证据不可实现）**：`packages/pi-subagents-enhanced/extensions/subagent-runtime.ts` 的 `subagentRuntime(pi: ExtensionAPI): void`/`installHeadlessTypedSubagentRuntime` 的 `registerAuthorizedRun?: (authorization: unknown) => Promise<void>`，以及 `packages/pi-subagents-enhanced/src/subagent-dispatch/extension.ts` 的 `executeCoding`、`executeGeneric` 和 `TypedSubagentExtensionOptions.registerAuthorizedRun?: (authorization: unknown) => Promise<void>`。将来若权威 adapter 可用，需要另行设计一个不丢失 binding 后 workspace receipt 的 typed Host 回调（建议消费 `{authorization: Readonly<RunAuthorization>, boundWorkspaceReceipt: <public managed-workspace.v2 receipt>, ownerReceipt: OwnerReceiptV1, executionLease: ExecutionLeaseV1, provenance: ProvenanceV1}`，其中 reference 由已冻结的权威 adapter 提供）；回调应位于两处 `bindRun` 成功后且持久化重放前，而不是在现有 `registerAuthorizedRun` 内凭 preallocate 值提前写入。`connectRuntimeCoordinator({pi,cwd,broker,stateRoot,rpc})` 处理恢复链时须单独核对 `activateResume` 的结果与 workspace rebind receipt，不能将新 run 的授权当作旧 workspace 已换绑。签名中 `<...>` 为待权威接口定义，并非已存在类型或批准实现。

## Residual risks / manual notes

- importer 搜索仅覆盖限定仓内 production roots；不证明仓外 loader 不存在。`coordinator-process.ts` 只沿用 `L-ORPHAN-WIRING.md` 的“外部 loader 未证实、保持 blocked-unknown”结论，本任务不接线、不删除。
- 即使 Broker `registerAuthorizedRun` 返回成功，对 generic facade 或无 AuthorityStore 的 legacy 模式仍不能证明 OwnerReceipt；supervisorControlPlane 缺失时返回 `undefined` 仅适于禁用功能，不能升级为 production inventory 输入。
- `InventoryV1` schema 检查四元格式而不检查外部 authority；后继须明确 source identity/clock/revision、receipt 变更时的 CAS 和 replay 时 stale inventory 处理，不得从测试成功推断生产 provenance。
