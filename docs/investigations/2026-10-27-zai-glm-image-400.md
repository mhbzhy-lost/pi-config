# zai-coding-cn/glm-5.3 读取图片 400 诊断

## 结论与证据边界

当前最有证据支持的归因是：**本机把仅声明文本输入的 `zai-coding-cn/glm-5.3` 覆盖成支持图片，Pi 据此生成图片消息，而用户提供的错误表明该次服务端校验只允许 `text`。首个可定位的声明偏离点是 `pi/models.json` 的 image override；请求与服务端不兼容发生在 content part 类型边界。现有证据不支持把问题定性为 Pi 图片格式转换缺陷。**

用户提供的错误是：

```text
Error 400 code 1210 messages.content.type 参数非法，取值范围 ['text']
```

本次只读核对对象为用户指定的 provider/model。现场配置与目录的精确 ID 均为 `zai-coding-cn/glm-5.3`；`glm5.3` 是用户非精确转述，不能作为另一个模型 ID。没有读取原始报错会话、活动 `model_change` 或实际 HTTP payload，因此**没有独立证明那次运行确实加载当前定义，也没有抓包证明那次请求的具体图片 part**。以下区分配置事实、代码可达行为和用户转述的服务端反馈。

检查依据为本机安装的 `@earendil-works/pi-ai` 与 `@earendil-works/pi-coding-agent`，版本均为 `1.4.0`。行号指本机安装文件，不代表其他 Pi 版本。未调用真实 provider，未进行网络测试，未访问 `auth.json`，未检索、解析或输出凭据字段；配置由本地脚本按非敏感字段白名单投影，未展示原文件全文。只新增本报告，未修改 production/config，未 stage/commit。

### models-store 不是最终配置，也不是手工修复入口

不能把 `models-store.json` 称为“所有 override 合并后的结果”。当前缓存仍是 `["text"]`，与本机 override 不同；代码解释了这一差异：

1. `node_modules/@earendil-works/pi-coding-agent/dist/core/model-runtime.js:88` 起为内置 provider 包装目录刷新，`:95` 调用 `withRemoteCatalog`。
2. 同包 `dist/core/remote-catalog-provider.js:69` 起提供缓存目录覆盖；`:77` 从 `context.stored` 恢复目录。`:129` 起将远端目录组成 `entry`，随后以 `persist: entry` 发布。缓存是否参与覆盖还取决于目录与内置数据时间比较（`:50` 起）。本次没有触发刷新。
3. `node_modules/@earendil-works/pi-ai/dist/models.js:153` 将 `publication.persist` 写到 models store；coding-agent 的 `dist/core/models-store.js:30` 默认存储文件是 `models-store.json`。这是目录缓存路径，不是用户最终配置输出路径。
4. `node_modules/@earendil-works/pi-coding-agent/dist/core/provider-composer.js:354` 明确将 `models.json.modelOverrides` 作为最上层用户覆盖；`:366` 按模型 ID 查 override，`:62` 执行 `input: override.input ?? model.input`。

因此，在正常加载当前配置且使用此模型的前提下，最终输入声明会是 `["text","image"]`，即使内置目录和缓存仍是 `["text"]`。手改缓存既不能撤回最上层 override，也会受目录刷新影响；本次不改缓存、安装包或配置。

## 图片从 read 到请求的生成链

下列链路由本地代码证明可达，不等同于已还原报错现场的请求：

```text
pi/models.json 的 glm-5.3.input 增加 image
  → provider-composer 最后覆盖模型输入能力
  → read 成功处理图片，产出内部 ImageContent
  → transformMessages 依据 input 判断是否降级图片
  → openai-completions.convertMessages 转成 image_url
  → buildParams 生成 model + messages
  → OpenAI SDK POST /chat/completions
  → 若服务端对该模型/请求只允许 text，则拒绝非文本 part
```

关键代码位置：

| 环节 | 文件与行号 | 行为 |
| --- | --- | --- |
| 图片工具产出 | `node_modules/@earendil-works/pi-coding-agent/dist/core/tools/read.js:84`、`:103` | 成功处理图片后返回文本说明和 `{type:"image", data, mimeType}`；`:40` 根据模型能力附加非视觉提示 |
| 能力门控 | `node_modules/@earendil-works/pi-ai/dist/api/transform-messages.js:38`、`:69` | 若 `input` 包含 `image`，保留图片；否则把用户或工具结果的图片转换为文本占位，用新消息对象承载转换结果 |
| 用户图片转换 | 同包 `dist/api/openai-completions.js:873`、`:901`、`:952` | 先调用 `transformMessages`，再把内部图片转换为 `type:"image_url"`，URL 为 `data:<mimeType>;base64,<data>` |
| 工具图片转换 | 同文件 `:1071`、`:1097`、`:1120` | 工具响应保留为文本 `role:"tool"`；有图片且声明支持图片时，图片作为随后 `role:"user"` 的 `image_url` part 发送 |
| 请求模型与消息 | 同文件 `:572`、`:577` | 调用转换函数，使用 `model: model.id`，所以这里的模型 ID 是 `glm-5.3` |
| 发送边界 | 同文件 `:187`、`:188`、`:197` | 生成参数后允许 `onPayload` 修改，再交给 `client.chat.completions.create`；本次未核验那次运行是否存在 payload hook |
| SDK 路径 | `node_modules/openai/resources/chat/completions/completions.mjs:19` | `create` 向 `/chat/completions` 提交请求 |

正常路径中的图片格式示意如下，省略实际图片数据：

```json
{
  "role": "user",
  "content": [
    { "type": "text", "text": "图片说明" },
    {
      "type": "image_url",
      "image_url": { "url": "data:image/png;base64,<图片数据>" }
    }
  ]
}
```

内部 `type:"image"` 会经过转换，不是原样发给 OpenAI Chat Completions。当前代码对用户图片和工具图片都生成 `image_url`；没有发现把 Anthropic `image/source` 或 Responses `input_image` 错塞入该 API 的证据。对工具结果而言，图片也没有直接塞进 `role:"tool"` 的 content 数组。

## 如何解读服务端错误

`messages.content.type` 指向消息内容分块的类型校验；`取值范围 ['text']` 表示**该次请求命中的校验规则只接受文本 part**。`image_url` 是非文本类型，因此上述生成行为与报错相符。仅凭这段错误无法确定被拒绝的是第几个消息，也不能确定请求实际发送的是 `image_url` 还是经 hook 修改后的其他类型。

需要区分两类问题：

- **配置能力声明不匹配：本地证据支持。** 内置目录与缓存的 `glm-5.3` 均为文本，本机 override 增加图片；Pi 按声明生成标准 Chat Completions 图片 part。用户提供的服务端反馈恰好限制为文本。首个可定位偏离点为能力声明，外部拒绝边界为 `messages.content.type`。
- **Pi 对已支持图像端点转换错误：尚无证据。** 这要求证明同一个 provider、base URL、模型 ID、账号/套餐实际支持某种图片协议，再证明 Pi 生成的格式与其要求不同。当前没有该具体端点与模型的成功图像记录或协议证据，不能因 400 就修改通用 adapter。

不能从模型名、同系列其他型号、其他区域、普通推理端点或其他厂商代理的视觉能力推出这里支持图片。内置目录中其他模型的 `image` 声明也不是 `glm-5.3` 的能力证据。

**该具体端点的 GLM-5.3 是否另有图像能力：本次无法独立证实。** 当前本地证据支持按文本模型处理；用户转述的报错支持该次请求只允许文本，但不足以证明所有账号、版本、路由在所有时间永久不支持图像。

## 最小修复建议

1. 对当前仅允许文本的使用方式，撤回 `pi/models.json` 中 `providers["zai-coding-cn"].modelOverrides["glm-5.3"].input` 的 `image`。可以删除这个 `input` 字段以继承目录的 `["text"]`，或明确设为 `["text"]`。如果该 override 只有这一个字段，可删除该模型 override；保留其他有意配置。本报告只提出建议，没有执行修改。
2. 通过 `/model` 重新加载配置并重新选择精确模型，或重启相关 Host，使内存中的模型定义更新。`node_modules/@earendil-works/pi-coding-agent/docs/models.md` 的“Configure a compatible endpoint”说明打开 `/model` 会重新加载 `models.json`。重新加载后应核对实际模型的有效 `input`，不能仅看缓存或 `enabledModels`。
3. 文本模型不能因此理解图片。本地 adapter 在 `input=["text"]` 时会发送文本占位，而非图片语义。若任务确实需要看图，应选择在**相应端点、具体模型和账号条件**下有图像能力证据的 provider/model；不能靠给当前模型添加 `image` 获得服务端能力。
4. 不建议为此修改 Pi 的通用 `openai-completions` adapter，也不建议把图片 base64 伪装成 `text`，或只将 `image_url` 改名为 `image`。这些做法都不能解决服务端只允许文本的限制。

若后续获得该具体模型/端点支持图像的可靠证据，再比较其要求的 part 类型、data URL/远程 URL 支持和角色约束。届时最小定位入口是 `openai-completions.js:952` 与 `:1097` 的图片转换，以及 `:188` 的 payload hook；只有证实端点要求与当前格式不一致，才考虑有范围限制的兼容修复。当前不提出代码补丁。
