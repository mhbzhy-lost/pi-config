## 0. 结论摘要

1. **首个偏离点不在 SDK 事件分发，而在上游 pi-subagents 的「两段唤醒」**：`pi-subagents@0.79.2` 的 `createParentWake` 在父会话 idle 时把 `triggerTurn:true` 的 `sendMessage` 改写为 `triggerTurn:false`（纯追加），再用另一条 `sendUserMessage(PARENT_WAKE_TEXT)` 启回合。这条纯追加的 custom message 走 Pi 的 `_appendCustomMessage()`，**只** `_emit()` 给 Host/RPC 监听器，从不进 `_emitExtensionEvent()`。
2. **这不是 1.3.0 引入的行为变化**：`_appendCustomMessage()` 在 `pi-coding-agent@1.0.4` 与 `1.3.0` 中逐字相同（已用 npm 缓存内 1.0.4 精确 tarball 只读对照）。真正的分界是 pi-subagents `0.75.0 → 0.76.1`（CHANGELOG #2688：notice 后追加 "Subagent updates above." 消息由后者启回合）。因此 `reports/recheck-host-lifecycle-1.3.0.md` §4.2「1.3.0 上 sendMessage 追加的 custom message 对扩展级 message_end 不可见」**事实正确，但归因需更正**：该不可见性在 1.0.4 就已存在，是 0.79.2 的唤醒路径把它变成了本仓注册面唯一依赖的路径。
3. **数据来源分类：第 1 类（预期 production 数据未被正确处理），不是 fixture 兼容问题**。判定依据不是「测试失败」，而是本仓自己的生产持久面：5 例 `workspace/supervisor-control/*.json` 全部 `requests: [] receipts: []`——生产注册函数根本没被调用；同时父侧 RPC 确实产生了完整的 `subagent_supervisor_request` custom 消息（含全部 `details` 逐字字段）。这排除了「fixture 缺件」「registered key 不匹配」两类解释。
4. **推荐的最小接入位置**：`packages/pi-subagents-enhanced/src/subagent-dispatch/extension.ts` 内新增 `pi.on("before_agent_start")` 账本扫描触发器，复用**同一个** `supervisorControlPlane.registerSupervisorRequest(details, hostRootSessionId)`；**保留**现有 `pi.on("message_end")` 注册面。不新增 sender、不改上游 `node_modules`、不改 membrane 的 raw 透传边界、不放松任何 gate。
   - 选择它而非「membrane `sendMessage` 代理」的关键理由：`before_agent_start` handler 是 **awaited** 的，位于首个 provider 请求之前，注册必然先于父模型可能发出的 `supervisor_request_reply`；membrane 观察点位于父唤醒同一同步栈内，与 fixture 的 2–9ms 父回合存在不可消除的竞态（见 §7.1）。
5. **fixture 的扩展级 `message_end` 观察必须另行迁移**（测试侧、只读迁移到既有 `parent-events.json` RPC records），但**不能**用它替代生产修复：即使 fixture 改成从 RPC 观察，durable `requests[]` 仍为空 → `supervisor_request_reply` 仍返回 `SUPERVISOR_REQUEST_NOT_PENDING` → child 仍超时。

### 2.2 已排除的两个替代解释

- **「注册发生了但 key（ownerGeneration/requestGeneration）不匹配」**：排除。`registerSupervisorRequest`（`src/subagent-dispatch/supervisor-control-plane.ts:272-286`）在 key 命中时返回 `{status:"registered", request: existing}`，任何一次成功进入都会在 durable `requests` 留下记录；5 例 `requests` 为**空数组**，只有「从未调用」能产生该状态。
- **「fixture 环境缺件（超时/身份/provider）」**：排除。`PI_INTERCOM_ASK_TIMEOUT_MS` 明显生效（invalid-reply 全例 3.9s、child 等待 ≈1.5s；其余 4 例 ≈20s）；父/子 `identities.allEqual===true`、`actualModel===joint-contact/fixture`、`runtimeAcknowledgedExtensions` 三项 required ACK 齐全（§4.1 已列）。

## 3. 5 例是否同类、分支差异

- **完全同类**：5 例走的是同一条 `parent-wake` idle 分支（`parent-wake.js:44-48`），事件下标逐条相同（custom 追加严格位于 `agent_settled` 之后、`agent_start` 之前），durable 状态同为 `0/0`。`managed`/`ceiling` 只是额外前置条件（真实 grant / child 工具面），不影响投递链。
- **分支差异（结构性分析，非本轮实测）**：
  | 父状态 | parent-wake 分支 | custom message 是否进 agent loop | 扩展 `message_end` | 现状 |
  |---|---|---|---|---|
  | idle | `:44-48`（append + 独立 wake user 消息） | 否 | **不触发** | **本轮 5 例即此分支，注册丢失** |
  | busy/streaming | `:40-43`（原样 `triggerTurn:true` → `agent.steer()`） | 是（`pi-agent-core/dist/agent-loop.js:117` 对 steer 消息 emit `message_start`） | 触发 | 注册仍可用（本轮未跑此类场景） |
  | 用户中断后 `held` | `:35-39`（`triggerTurn:false` 纯 append） | 否 | 不触发 | 同样丢失；随后无 wake，直到父下一次回合 |
- 这解释了该缺陷为什么此前未被发现：真实生产中父会话在 child 提问时**多数并不 idle**（busy 分支恰好仍能工作），而 fixture 刻意构造了 idle 父；而 idle 恰恰是 0.76.1 那套两段唤醒要解决的目标场景，因此**生产可达**（后台 run 在父 idle 时提问是设计用途本身）。

## 6. 上游是否提供「追加 custom message」的公开扩展事件

**没有。** 逐条核对（`dist/core/extensions/types.d.ts:1081` 的 `ExtensionEvent` 联合）：

- 有：`message_start/message_update/message_end`（均源自 agent loop 管线）、`turn_start/turn_end`、`agent_start/agent_end/agent_before_settle/agent_settled`、`context/context_with_system`、`before_agent_start`、`before_provider_request`、`tool_*`、session 生命周期。
- 没有：任何等价于 `entry_appended` / `custom_message_appended` 的扩展事件。`entry_appended` 只经 `_emit` 给 Host（`agent-session.js:187/477/640/853`），扩展不可见。
- `docs/extensions.md` 仅承诺：`message_end` 可替换「已 finalize 的消息」（`docs/extensions.md:106`）；`sendMessage` 的定位是「Custom content stored and sent to the model」（`:233`），未承诺扩展事件。`docs/message-types.md:226` 定义 `role:"custom"` 但无事件语义。
- 结论：**不存在可直接替代 `message_end` 的扩展级 hook**；只能在本仓边界上做被动观察，或要求上游改（`_appendCustomMessage` 派发扩展事件 / pi-subagents 改用可启回合的发送），后者属产品决策，超出本仓可单方面修改范围。

## 7. 候选接入点比较（含信任依据与复用函数）

三类候选都必须满足：**逐字透传** `content/details/options`、**不新增 sender**、**不从通知文本正则取授权**、**不从 RPC/stderr 事件伪造 authority**、**不改上游 node_modules**、**不放松 gate**、**不兜底注册任意请求**。

现有可复用接口（全部已经存在，无需新建权威）：

- `supervisorControlPlane.registerSupervisorRequest(details, hostRootSessionId)`（`supervisor-control-plane.ts:272-286`，幂等 key = `root:runId:ownerGeneration:requestId:requestDigest`）；
- `extensions/subagent-runtime.ts:301-306` 的 `enabledSupervisorControlPlane` 包装：`if (!brokerReady || !broker || root !== broker.rootSessionId) throw ROOT_BROKER_UNAVAILABLE`，并追加 `correlation = await captureSupervisorCorrelation(broker, native)`；
- `captureSupervisorCorrelation`（`src/subagent-dispatch/supervisor-consumption.ts:30-45`）：校验 `status.json` 身份、`steps[childIndex].agent`、session 文件在受信根内，再用官方 `SessionManager.open` 读 **child canonical 会话**，要求恰好存在 **1 个** 未被 toolResult 闭合、`reason` 与 `requestBody` 完全匹配的 `contact_supervisor` toolCall。→ 这就是 authority 的真正来源；请求消息文本本身**不是**授权依据；
- `resolveRootSessionId(sessionManager)`（`src/subagent-dispatch/root-broker-protocol.ts:350-353`）；
- `registrationFailures` + `reportSupervisorDiagnostic` + `subagent_supervisor_registration_failed` 失败回执（`extension.ts:2048-2058`），以及 reply 侧的 `SUPERVISOR_REQUEST_REGISTRATION_FAILED`（`:1590-1596`）。

### 7.1 方案 A：membrane `sendMessage` 观察点（`runtime-membrane.ts:156-177`）

- 形态：在既有 proxy 内，`target.sendMessage(visible, options)` 返回后，若 `message?.customType === "subagent_supervisor_request"` 就回调一个注入的观察者（该 proxy 已有同类旁路诊断 `traceWorkingState("send-message", …)`），把 `message.details` 原样交给同一个 `registerSupervisorRequest`。
- 优点：触发最早；覆盖 idle / busy / held **全部**分支；`content/details/options` 天然逐字（只读不改）；不新增 sender。
- 致命短板（时序）：`parent-wake.js:44-48` 在同一同步栈内先 `sendMessage` 再 `sendUserMessage`，两者都不被 await。观察者只能与父回合**并发**跑注册（broker IPC + `loadRoot` + `captureSupervisorCorrelation` 读过 child session + 带 `handle.sync()` 的锁写入，均为多毫秒级、跨多个 macrotask），而 fixture 父回合仅 2–9ms（custom `…767` → reply 结果 `…776`）。即注册**可能**晚于 `supervisor_request_reply`，本 5 例是否转绿不可保证。
- 若为了让注册先于 wake 而把 append 延后（await 注册再 `target.sendMessage`），会翻转同栈顺序：wake user 消息先启动回合，custom message 落进 `_pendingCustomMessages` 被推迟到回合末（`agent-session.js:1836-1845`），父模型在该回合看不到请求正文 → **改变生产语义，不可接受**。

### 7.2 方案 B（推荐）：`pi.on("before_agent_start")` 账本扫描

- 形态：新增一个纯观察型 handler，扫描当前会话**活跃分支**（`ctx.sessionManager.getBranch()`，条目形如 `{type:"custom_message", customType, content, display, details}`，见 `dist/core/session-manager.js:165-183`、`:947-960`），对 `customType === "subagent_supervisor_request"` 且未注册过的条目，调用与现有一致的 `registerSupervisorRequest(entry.details, resolveRootSessionId(ctx.sessionManager))`。`details` 是持久化时的原对象，逐字透传。
- 时序优势（决定性）：`_startRun → _prepareRun` 中 `await this._extensionRunner.emitBeforeAgentStart(...)`（`agent-session.js:1457`）位于 `agent.prompt()` 之前，且 handler 被 await。挂在 wake 回合上时，**注册必然先于该回合的首个 provider 请求完成**，父模型任何 `supervisor_request_reply` 都排在注册之后 → 无竞态、无 sleep、无轮询。
- 触发完备性：
  - idle 分支（5 例）：wake 回合即触发 ✔；
  - `held` 分支：无 wake，但父下一次起回合时扫描 → 注册 ✔（此前父没有回合计可发 reply，语义自洽）；
  - busy/steer 分支：该回合已在运行，`before_agent_start` 已过去 → 仍由**保留的** `message_end` handler 覆盖（steer 消息经 `agent-loop.js:117` emit `message_start`，故扩展事件成立）。
- 与既有实现的关系：把 `extension.ts:2036-2062` 的 handler 主体抽成 `registerSupervisorRequestFromMessage(message, sessionManager)`，`message_end` handler 与新 `before_agent_start` 扫描**共用**它；`message_end` 一行保留（零行为变更），新 hook 仅追加。

- 必须遵守的实现约束（否则会引入新问题）：
  1. **跳过已注册请求**：`captureSupervisorCorrelation` 的匹配集排除已完成 toolCallId，回执被消费后再观察会得到 `calls.length !== 1` → `SUPERVISOR_CORRELATION_CALL_AMBIGUOUS`。扫描必须先 `await supervisorControlPlane.findRequestAsync(details.id, root)`（`:502-506`，与 reply 路径同一接口）判定「从未注册」，否则每回合都会打 `subagent_supervisor_registration_failed` 噪声并污染 `registrationFailures`。每代实例可另加内存 Set 作为纯优化（不能替代 durable 判定，reload 后失效）。
  2. handler 返回 `undefined`（不得返回 message/systemPrompt，避免影响回合）。
  3. 失败走既有回执路径（`registrationFailures` + diagnostic + `subagent_supervisor_registration_failed`），不 throw、不 retry、不 fallback 注册。
  4. 扫描按 branch 顺序、串行 await；只对「未注册」条目产生 IO（`getEntries()` 会拷贝整会话，`getBranch()` 已足够且限定活跃分支）。

### 7.3 方案 C：`context` / `context_with_system` 事件观察

## 12. 残余风险

1. **观察通道的信任等级**：方案 B 以「会话账本中的 custom 消息」为触发。任何同进程扩展都能写出同 `customType` 的消息；现状（`message_end`）同样如此，未降级。真正的权威仍是 broker owner receipt + child canonical 会话比对。若要求更强，只能等上游提供生产侧登记回调（方案 D），本仓不预置兜底。
2. **扫描范围与分支**：使用 `getBranch()`（活跃分支）可避免注册废弃分支上的请求；改用 `getEntries()` 会把已放弃分支的请求也纳入。实现时须明确选择，且幂等 key 依赖 durable 记录仍在（若某 root 的 durable 状态被清理，重放可能重新登记为 pending）。
3. **`findRequestAsync` 前置检查的竞态**：两次观察（`message_end` 与 `before_agent_start`）理论上可同时通过「未注册」检查，导致重复调用注册。核心注册幂等（同 key 返回 existing），重复代价是多余一次 `captureSupervisorCorrelation`；若第二次在回执消费后执行则会抛 `SUPERVISOR_CORRELATION_CALL_AMBIGUOUS` 并产生一条噪声回执 → 建议实现时用「按 requestId 的单飞 Promise」串行化（与 `registrationFailures` 同层，最小改动），避免噪声。
4. **`before_agent_start` 延迟**：注册落到回合起始路径上，会给每个「有未注册请求」的回合增加一次 broker+fs+child-session 读取（毫秒级）。只在有待注册请求时发生，不改变 prompt/工具面。
5. **仍未修复的同类面**：`subagent-notify`（完成通知）扩展级观察缺失；TUI 投影（`completion-notices.ts`）在同机制下静默失效。本报告只给关联证据，未给结论。

## 14. 实施方案记录（方案 B，独立实施步，未验证）

### 14.1 改动范围

唯一 production 文件：`packages/pi-subagents-enhanced/src/subagent-dispatch/extension.ts`（原 `message_end` 注册面所在块）。未改 gate / protocol / membrane / supervisor-control-plane / upstream `node_modules` / 任何 test 或 fixture，未新增测试，未新增依赖或模块。

### 14.2 实现形态

1. **抽出唯一的观察→注册实现** `observeSupervisorRequest(details, scope, { skipRegistered })`：
   - `details` 是 `message.details` 或账本条目 `entry.details` 的**原对象**，逐字传入 `supervisorControlPlane.registerSupervisorRequest(details, scope.rootSessionId)`；不增删字段、不改写 `content`/`display`/`options`、不构造 correlation（correlation 仍由 `enabledSupervisorControlPlane` 包装置入，来源不变）。
   - 身份与授权链完全沿用原路径：`enabledSupervisorControlPlane` 的 broker ready + `root === broker.rootSessionId` 相等门禁 → `readOwnerState` 三态 → owner/`ownerGeneration`/`requestGeneration` → `captureSupervisorCorrelation`（child canonical 会话里唯一未闭合 `contact_supervisor` toolCall 匹配）。未新增 sender、未新增授权来源、未直接读取 raw authority 放行。
   - 失败仍走既有路径：`registrationFailures`（reply 侧 `SUPERVISOR_REQUEST_REGISTRATION_FAILED` 项目面）+ `reportSupervisorDiagnostic(phase:"supervisor-registration-failed")` + `subagent_supervisor_registration_failed` 回执消息，文案与投影字段不变。
2. **保留 `message_end` 入口**（busy/steer 分支仍靠它）：`customType !== "subagent_supervisor_request"` 早退、`disposed`/`token` 守卫、`onSupervisorRequest` 回调顺序均保持原样，只把 body 换成调用抽出函数。
3. **新增 `before_agent_start` 观察入口**（idle/held 两段唤醒）：
   - 只读 `ctx.sessionManager.getBranch()`（**活跃分支**），筛 `entry.type === "custom_message" && entry.customType === "subagent_supervisor_request" && typeof entry.details?.id === "string"`；不用 `getEntries()` 回放整会话，不遍历废弃分支。
   - 逐条 **串行 `await`** 注册；Host 在 `_prepareRun` 里 `await emitBeforeAgentStart(...)` 且位于 `agent.prompt()` 之前（`agent-session.js:1457`），因此注册必然先于本回合首个 provider 请求，父模型任何 `supervisor_request_reply` 都排在注册之后——无 sleep、无轮询、不参与 membrane 异步赛跑。
   - handler **返回 `undefined`**，不返回 `message`/`systemPrompt`，不改变回合输入与工具面。
4. **跳过 durable 已注册请求**（防复活已消费 toolCall）：扫描路径先 `await supervisorControlPlane.findRequestAsync(details.id, scope.rootSessionId)`，键取 `details.id`（注册函数 `requestId = native.id`，不猜多键 fallback）；命中即跳过（含已完成/过期记录）。`findRequestAsync` 抛错时不注册、fail closed，并把该 requestId 记入既有 `registrationFailures` + diagnostic（不静默吞掉、不盲重试）。
5. **并发单飞（本实例、短生命周期）**：以 `root + sessionId + requestId` 为键的 `Map<string, Promise>`（以 NUL 分隔各分量），`message_end` 与账本扫描对同一 root+session scope+requestId 的在途注册复用同一 flight，settle 后删除；不落盘、不跨 root 复用、不构成新的持久权威。
6. **生命周期与失败收敛**：flight 内注册前再校验一次 `disposed || registry.get(pi)?.token !== token`（stale scope/disposed 实例不注册）；旧实例的待完成 flight 使用其调用时捕获的 scope root，且注册门禁要求 root 等于 broker root，因此不可能落到新 root。本代实例内已失败的 requestId 由 `registrationFailures` 记忆并在后续扫描中跳过，避免每回合重放同一失败条目产生持续告警；跨代（reload）最多再尝试一次，不新增长期重试/TTL 权威。扫描期异常只进 diagnostic（`supervisor-registration-scan-failed`），不打断回合。
