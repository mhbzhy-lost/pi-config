# Pi 1.0.4 → 1.3.0、pi-subagents 与 scheduler 联动升级初步调研

调研日期：2026-10-21。代码基线：`1246db36df50`，包含调研时工作区的现有改动。本文是升级成本评估，未执行依赖升级或修改运行配置。

**建议与成本**

建议采用 **Pi 四核心包 `1.3.0`、`pi-subagents@0.79.2`，scheduler 与 pi-shared 暂留 `0.1.9`**，先在隔离安装中验收，再替换正式运行环境。scheduler 不存在已确认的强制联动升级要求；升级它的结构化结果合同应单独适配。`0.78.0` 是修复 Pi 1.2+ 后台启动的最低版本，可作为范围较窄的候选；它没有后续版本对恢复、通知、宿主选择等问题的修复。

对本仓而言，升级成本为中等。初估 **2–4 人日**：约 0.5–1 人日处理依赖、版本门禁、兼容入口及现有测试适配，余下用于真实 Host/child、通知、恢复、workspace 与 TUI 回归。若要求完整维持旧版长结果投递或会话所有权语义，而新上游行为与之冲突，需在隔离验证后重新估算；现有证据不足以承诺只是修改版本号。

Pi 本体的类型迁移量较小；主要不确定性来自 `pi-subagents` 0.75 → 0.79 的行为变化，以及本仓增强层对它的封装。

以下行为虽然多列在 Fixed/Changed 中，也应作为升级验收项：

- 恢复会话会还原历史 active tools；`--tools +name/-name` 叠加历史集合，明确工具名、`--no-tools` 等仍可覆盖。需确认旧 session 不会恢复本仓不应暴露的 upstream union 工具。
- 裸 `--model` 多 provider 命中时优先有凭据者，否则报告歧义；`--models`、`enabledModels` 可对多个 provider 展开。本仓 dispatch 的模型选择需要保持精确 provider/model 约束。
- print 模式最终输出达到 token 上限时会退出 1，旧自动化若把它当成功要改。
- 最终 tool arguments 不是合法 JSON object 时，新增 `argumentsError` 并使调用验证失败；不再用局部解析结果执行。
- 跨模型切换丢弃先前模型的 thinking，`serializeConversation()` 在 compaction、branch summary、bug report 中也不再包含 thinking。历史 session 格式不需要因此批量改写。
- 内部 Pi 依赖改为精确版本，消除了 1.0.4 的 `^` 范围导致的核心包混装来源；根项目仍需维持四核心、两个安装根与 physical peer 绑定的一致性。

**为什么必须升级 pi-subagents，以及选哪个版本**

`0.75.0` 的 `resolveHostPeerAliases()` 对非早期 0.x 宿主都要求 chord。Pi 1.2+ 不再声明或安装 chord，干净安装下会导致后台子进程不能启动。残留 node_modules 中的 chord 可能掩盖该问题，不能据此判断旧版可用。

| 候选版本 | Pi 1.3.0 相关判断 | 建议 |
| --- | --- | --- |
| 0.75.0 / 0.76.x / 0.77.0 | chord 必需假设尚未修复；peer dependency 的 `*` 不代表可运行 | 排除作为目标 |
| 0.78.0 | 发布说明明确修复 Pi 1.2.0 的 chord 启动问题；同时修复 Esc 后被完成通知重新唤醒、capacity 泄漏等 | 最低后台启动兼容候选；若 0.79 会话接管确有阻塞，可用于缩小比较范围，仍需完整验收 |
| 0.79.0 | 改进 retained/forked child resume；适配 Pi 1.2+ custom before_agent_start，避免 watchdog 把 system prompt 当用户需求；增加同进程 session succession | 有需要的修复，但后续补丁更完整 |
| 0.79.1 | child 优先使用嵌入应用的真实 Pi；修复 runtime 更新后工具恢复与 workflow child 结果，调整 bg_wait/supervisor 的动态激活 | 对本仓 physical Host 绑定有价值；不应停在首个 0.79.0 |
| 0.79.2 | 增加排队完成通知的持久化重放、steer 超时解锁、workflow capacity 修复、旧 compaction 的工具恢复修复，以及 APPEND_SYSTEM 隔离 | 推荐精确锁定的验收目标；发布较新，尚无本仓运行验收结论 |

0.75.0 与 0.79.2 的公开 exports 集合一致。本仓直接消费的 root registration、`agents`、`capability-ceiling`、`required-child-extensions` 声明，以及相关注册参数声明逐字一致。当前 `src/compat/pi-subagents-0.75.ts` 实际主要封装公开 root/agents 与本地 transcript 逻辑，未发现其中仍有 upstream 深层 import；因此没有证据支持需要大规模改写兼容层。兼容入口命名、规范与验收基线仍需随版本同步，不能保留“已验收 0.75”作为新版本保证。

**Scheduler 是否需要联动升级**

补查日期：2026-10-21，工作区基线 `e2d38f2e3b81`。结论是：**为完成本轮 Pi 1.3.0 升级，建议先保留 `@amaster.ai/pi-task-scheduler@0.1.9`、`@amaster.ai/pi-shared@0.1.9`、`croner@10.0.1`；没有发现必须升级 scheduler 的接口依赖。若决定接入新版结果合同，则以 `0.1.29` 为目标，额外处理 adapter。** 这不是宣称 0.1.9 已经过目标 Host 的真实运行验收。

本仓禁用 upstream package 的自动发现资源，只由 `pi/extensions/task-scheduler.ts` → `src/task-scheduler/adapter.ts` 调用其 default factory。adapter 只暴露 session_start/session_shutdown、受控注册、sendUserMessage，保留 create/list/get/delete 四工具，全部为 `model-only`。因此应比较真实发布源码与本仓 facade，而不能只依据 npm peer 范围或 monorepo 升级标题决定。

官方 registry 的 scheduler `latest` 为 `0.1.29`，发布于 2026-10-20；开发依赖 Pi `1.3.0`、TypeBox `1.3.27`，运行 peer 仍为 Pi `>=0.79.1`，pi-shared 精确依赖 `0.1.29`。release 所说的“升级 Pi runtime 1.3.0”在该包 metadata 中主要体现为开发基线更新，并非新增 Pi 1.3 的硬性 peer 下限。

| 已比较的版本 | 发布文件事实 | 对本仓的价值与成本 |
| --- | --- | --- |
| 0.1.9 → 0.1.24 | `extension.js`、`tools.js`、`index.js`、`stores.js`、`json-file.js` 逐字一致；0.1.24 的 Pi 开发基线为 1.0.4 | 没有已识别的 scheduler 运行时修复收益，不建议为换版本号增加安装/门禁改动 |
| 0.1.25 | Pi 开发基线转到 1.2.0；runner 的唯一代码变化是显式 `sendUserMessage(prompt, { deliverAs: 'followUp' })`；tools 新增结构化结果与输出上限 | 本仓 adapter 已默认补 followUp，并强制关闭 prompt template 展开，旧版在 busy/startup 投递时缺 deliverAs 的问题已被覆盖；结果合同变化需要适配 |
| 0.1.26–0.1.28 | 采样的每个版本仍有 followUp 与 structured results；调度核心、Store 和 JSON writer 与 0.1.9 一致 | 未发现对本次 Host 兼容必须的核心修复 |
| 0.1.29 | Pi 开发基线为 1.3.0；extension/tools 与 0.1.25 逐字一致，调度核心、Store、Lock、JSON writer 仍与 0.1.9 一致 | 如决定升级，选择同版 scheduler + pi-shared 0.1.29；不用先停在 0.1.25。但必须把结果合同接好 |

旧 scheduler 只订阅 session_start/session_shutdown，不消费 before_agent_start 的旧 prompt 字段，也不使用 chord、实验 SDK 或已删除的 frame API。它的 `sendUserMessage(task.prompt)` 在进入本仓 adapter 后实际带 `{ deliverAs: 'followUp', expandPromptTemplates: false }`，所以单凭 Pi 1.2 的 busy 语义变化，不能推出本仓必须换 scheduler。Pi 1.3 的真实 busy/idle/启动准备期投递仍要验证。

`0.1.25+` 对当前 adapter 有明确的不兼容：

- 新 `textResult()` 总会填写 `details` 和 `structuredContent`，并为工具声明 `outputSchema`。list 的结构化值是 `{ tasks, total, truncated }`，get/create 是 `{ task, truncated }`，delete 是 `{ taskId, deleted, truncated }`，错误结果还带 `isError: true`。
- 当前 `boundedResult()` 在 `src/task-scheduler/adapter.ts:196` 明确拒绝任何已定义的 `details`，所以合法的新 list/get 结果会抛 `unsafe scheduler result`。`parseSchedulerObservation():292` 同样先拒绝 details，因此 footer/source 的任务观察会进入 unavailable/stale，而非获得新列表。
- 新版模型可读 text 先限制为 16KiB/200 行，结构化通道限制为 12KiB/100 条完整记录。现有 observer 依赖完整 raw text JSON 数组，升级时必须处理新 envelope、`total/truncated` 和记录级截断，不能把缺项当作任务不存在。
- 本仓四工具为 `model-only`；新版用于脚本消费的结构化结果收益不会自动成为本仓可用的 codemode 能力。是否开放脚本调用是独立产品选择，不属于“升级版本”隐含授权。
- get 不再输出 `lastError`、run-history 的原始 `message`，部分错误改为固定文案；既有错误观察合同也需核对。新版 tools 还新增了对 physical Pi SDK `truncateHead` 的运行时 import，需要确保解析到目标 Host 的依赖闭包。

这是新版合法生产结果与旧 adapter 合同不一致的迁移问题。不能通过直接清空 details、丢弃 structuredContent、删除扫描或放宽工具门禁绕过。适配范围应同时覆盖 text/structured 通道的持久化内容扫描、有界输出、schema 一致性、观察投影与错误通道，继续保留四工具与 session/epoch 隔离。

当前上游 `stores.js`、`json-file.js` 和调度 `index.js` 在 0.1.9 与 0.1.29 之间逐字一致，所以不能把已有 Store 缓存/并发、Lock 或跨 Host 最新状态缺口写成“新版顺便修复”。它们不因这次版本更新自动解决。
