# Scheduler 合并收尾核验：0.1.9 保留 vs 0.1.29 并入 Pi 1.3.0 升级

核验日期：2026-10-21（补查）。代码基线：`35e3e77`（工作区含未提交的 `.gitignore` 修改与若干未跟踪物，均未由本次任务触碰）。
本文是**只读核验报告**：只陈述发布源码与本仓 adapter 的事实、合同差异与建议边界，不含实现计划，不含新增测试授权，不触发任何 scheduler / Host / child 任务。

## 一、结论摘要

1. **`0.1.29` 没有解决本仓记录的任何遗留并发/缓存/owner 隔离问题。** 调度核心 `index.js`、Store/Lock `stores.js`、JSON 写入 `json-file.js` 在 `0.1.9` 与 `0.1.29` 之间**逐字一致（sha256 相同）**；`extension.js` 全文件只有一个字符级差异，即 runner 显式带上 `{ deliverAs: 'followUp' }`。`0.1.29` 的 release notes 也没有 scheduler 修复项，只有 "upgrade Pi runtime to 1.3.0"。
2. **`0.1.29` 与 `0.1.9` 的真实差异全部落在 `tools.js`（结构化结果合同）与 `pi-shared` 新增的 `boundStructuredContent`。** 这不是并发修复，而是**返回形状变更**；它与本仓现有 adapter 的"拒绝 `details`"安全包装**正面冲突**，且冲突是硬失败（每次 `scheduler_list` / `scheduler_get` 调用都会抛 `unsafe scheduler result`），不是显示层差异。
3. **没有发现 scheduler 必须跟着 Pi 1.3.0 走的硬依赖。** `0.1.29` 新增的 `truncateHead` 运行时 import 在当前安装的 Pi `1.0.4` 中已导出（`dist/core/tools/truncate.js:44`，`{maxBytes,maxLines}` 选项与上游用法一致）；`outputSchema` / `structuredContent` 在 Pi `1.0.4` 类型与运行时已存在（`types.d.ts:461,959`；`agent-session.js:358`）。`0.1.29` 的 peer 仍是 `@earendil-works/pi-coding-agent >=0.79.1`，与 `0.1.9` 相同。
4. **建议：本轮按"保留 0.1.9 + 一起升级 Pi"收尾，scheduler 结构化结果合同另立独立事项（拆后续），不并入 1.3.0 升级批次。** 理由不是"0.1.9 更好"，而是：升级 `0.1.29` 换不到任何遗留缺陷的消除，却要把一个尚未裁决的产品语义（是否接受 `details`/`structuredContent` 通道与上游 16KiB/100 条截断）压进同一次升级的验收里，使 Pi 1.3.0 的回归结论无法与 scheduler 合同变更解耦。
5. **`0.1.9` 也没有被证明已在新 Host 上运行验收。** 保留它意味着把 assessment 已列的 scheduler 真实回归项带入本轮，这些项**不可跳过**（见第五节）。

## 五、保留 0.1.9 与升级 0.1.29 的真实合同差异

### 5.1 0.1.25+ 的结果合同与本仓 adapter 的具体碰撞

| # | 上游 0.1.29 事实（源码） | 本仓现状（源码） | 后果 |
| --- | --- | --- | --- |
| 1 | 所有成功/失败结果都带 `details` 与 `structuredContent`（`textResult()`） | `boundedResult()`：`result.details !== undefined` 即 `throw new Error("unsafe scheduler result")`（`adapter.ts:196`） | **`scheduler_list` / `scheduler_get` 每次调用必然抛错**。这不是显示层降级，而是四工具中的两个直接不可用（`adapter.ts:332`） |
| 2 | 同上 | `parseSchedulerObservation()`：`details !== undefined` → `{kind:"malformed"}`（`adapter.ts:292`） | observer 刷新恒为 malformed → `applyErrorLabel("malformed")`，有旧观察则 stale 保留旧 records，否则 unavailable；footer 仍会走 `schedulerFooterStatus()`（该函数不看 details） |
| 3 | list 文本先经 `truncateHead` 限 16KiB/200 行，结构化通道 `boundStructuredContent` 限 100 条数组元素 / 12KiB | 既有观察合同要求"缺项不得当任务不存在"，且不得反解析被截断输出 | **新的截断源出现在"raw 上游结果"内部**：任务多到文本被切时 `JSON.parse` 失败 → 同一 `malformed` 分支；`total` / `truncated` 只存在于被拒绝的 `details` 通道，文本通道没有补数能力。这是产品语义缺口，不是修 bug |
| 4 | `create`/`delete` 结果透传时携带 `details = {task:{…,prompt: 完整原文}}` / `{taskId,deleted}`（`boundStructuredContent` 只压 100 条、12KiB，不删 prompt） | `wrapTool` 对 create/delete **不走 `boundedResult`，原样透传**（`adapter.ts:333`、合同 `docs/architecture/task-scheduler-adapter-contract.md`「create/delete 的上游结果原样透传」） | 完整持久化 prompt 会进入 `details`。Pi 的 `createToolResultMessage()` **只持久化 `content` 与 `details`，不持久化 `structuredContent`**（`pi-agent-core/dist/agent-loop.js:649-663`），因此新 `details` 会被写进 session 历史与 renderer 可见面，且不经过 `PERSISTED_HEADER` 不可信来源边界 |
| 5 | 四个工具声明 `outputSchema` | `wrapTool` 用 `...definition` 传播定义，`outputSchema` 因此被带到宿主；但 list/get 的返回恒为 `details: undefined`，无 `structuredContent` | 与 Pi 文档约定不一致（`docs/extensions.md:146`"declare `outputSchema` and return a matching `structuredContent`"）。Pi 1.0.4 未见运行时校验/强制（`tool-definition-wrapper.js` 仅透传），所以是合同漂移而非立即崩溃 |
| 6 | `scheduler_get` 不再输出 `lastError`，`runHistory` 条目去掉 `message`；错误文案改为固定字符串（`console.error` 只进宿主 stderr） | adapter `detail()` 依赖受控 `scheduler_get` 包装（`adapter.ts` observer.detail），`docs/plans/records/2026-10-13-scheduler-observer-contract.md:174` | 详情面/诊断可见字段减少；原先可从错误文本读到的原因变为固定文案，可诊断性下降 |
| 7 | `scheduler_delete` 失败改为 `isError:true` + "Task not found: id" | 合同要求"删除失败以 'Task not found' 文本或异常可观察呈现" | 语义仍满足，但 `isError` 语义是新增形态，需要核对消费者 |
| 8 | 空列表哨兵 `"No scheduled tasks."` 保留 | `NO_TASKS_SENTINEL` 依赖该精确文本 | **仍兼容**，这一点不构成差异 |

补充事实（不是差异，但影响"能否只升 scheduler"）：`tools.js` 顶部 `import { truncateHead } from '@earendil-works/pi-coding-agent'` 在 Pi `1.0.4` 已可用（`dist/index.js:30` 导出，实现 `core/tools/truncate.js:44`，`options.maxBytes/maxLines` 语义一致）。因此**"0.1.29 需要 Pi 1.3"这一直觉不成立**；真正强制的是 `pi-shared` 必须同为 `0.1.29`。

### 5.2 自建 followUp 补丁的处置条件

现状（`adapter.ts:481`）：facade `sendUserMessage` 固定追加

```
{ deliverAs: "followUp", ...options, expandPromptTemplates: false }
```

- 对 `0.1.9`：上游 runner 只传 `pi.sendUserMessage(task.prompt)`，**本仓默认值是被 Pi 1.2+ 的 busy/启动准备期语义保护的唯一来源**；`expandPromptTemplates:false` 同时阻止触发文案被当作扩展命令/模板展开。这部分是承重结构，不是冗余。
- 对 `0.1.29`：上游显式传 `{ deliverAs: 'followUp' }`，经 `...options` 展开后与本仓默认同值，**行为等价，本仓默认值退化为防御性重复**；`expandPromptTemplates:false` 上游仍未设置，**必须保留**。
- 因此"删掉自建 followUp"的成立条件是可判定的三条同时满足：(a) 目标版本 ≥ `0.1.25`（上游自身带 `deliverAs`）；(b) adapter 继续保留 `expandPromptTemplates:false` 与整段 routing context 注入；(c) 在目标 Host 上实测 idle、busy、`before_agent_start` 准备期三种时机的投递都被归入 followUp 且不丢消息。**只要版本留在 0.1.9，就不能删**——删掉即退回 Pi 1.2+ 的行为缺口，且没有任何替代来源。
- 反向不成立：升级 0.1.29 **不需要也不允许**顺手删除 `PERSISTED_HEADER` / `ROUTING_CONTEXT` 注入，它们与版本无关，是内容来源标记与自清理路由合同。

## 六、若保留 0.1.9：本轮不可跳过的验收项

这些不是"可选项"，而是保留旧版后必须自身承担的风险面（沿用 assessment 已列条目，逐条给出不可跳过的理由）：

| 验收项 | 不可跳过的理由 |
| --- | --- |
| idle 触发、busy 触发、`before_agent_start` 启动准备期触发三种时机 | Pi 1.2 起 run 从启动准备期就算 busy，`sendUserMessage` 必须带 `deliverAs`。本仓默认值虽已补上，但**从未在 Pi 1.3.0 上实测**；这是当前唯一的正确性依据 |
| `/reload`、同 session `resume`、`new`、`fork`、`pi -c` 后任务恢复与旧 timer 清理 | adapter 的 epoch/失效清场逻辑是自建的，Pi 1.3.0 的 session 生命周期变化直接决定它是否仍成立 |
| 切换 session 后旧 timer 停止、旧 listener 清场、旧代 token 全部失效 | 同上；`session_shutdown` 顺序冻结在 `adapter.ts` 闭包里，需真实观测 |
| 四工具（list/get/create/delete）可用、`update`/`run_now`/`/cron` 仍被丢弃、全部 `model-only` | 门禁是本仓合同，任何一次注册面变化都可能导致越权暴露 |
| observer 刷新 + footer 状态 + `detail()` 三态（available/stale/unavailable） | 依赖上游 `list` 文本 JSON 数组与 `No scheduled tasks.` 哨兵；Pi 1.3.0 下若工具 ctx 语义变化，`refresh` 的 token 匹配与 initial refresh 仍需实证 |
| 触发消息完整链路（来源标记 + prompt + 边界行 + routing context，`expandPromptTemplates:false`） | 是"模型不会被持久化内容劫持"的唯一执行期边界 |
| 敏感结果扫描 / secret / injection / 不可见 Unicode 扫描未退化 | 扫描在 `boundedResult` 与 `parseSchedulerObservation` 两处，均需在真 Host 上确认未被新事件路径绕过 |

保留 0.1.9 **不产生**的额外成本：不需要动 `tools.js` 返回形状适配、不需要处理 16KiB/100 条截断语义、不需要重新裁决 `details` 通道。

## 七、若改 0.1.29：哪些自建代码可删、哪些必须保留

**可删除/可退化的，只有两类，且都有前置条件：**

1. adapter 的 `deliverAs:"followUp"` 默认值——前置条件见 5.2 三条（可删但收益接近零）。
2. 无其它。`src/task-scheduler/adapter.ts` 中**没有任何一段代码是为"补偿上游缺结构化结果"而写的**，所以升级不会换来"删掉一坨自建代码"。

**升级 `0.1.29` 后仍必须保留的自建面（缺一即破坏既有合同）：**

| 保留项 | 位置 | 为什么版本升级不能替代 |
| --- | --- | --- |
| 敏感/注入/Unicode 扫描与 1MiB 输入审计 | `boundedResult`、`parseSchedulerObservation`、`scanPersistent`、facade `sendUserMessage` | 上游只在**输入**侧做 `boundStructuredContent` 的体积裁剪，不做 secret/injection 判定；扫描面还需覆盖新出现的通道（text 与既有 `details`） |
| 有界输出（50KiB/2000 行）+ 固定来源标记 + `truncated` 标记 | `boundedResult` | 上游 16KiB/200 行是**模型可读文本**的裁剪，不等于本仓输出合同；且两者截断语义不可互相冒充 |
| 四工具白名单 + `exposure:"model-only"` | `wrapTool`（`adapter.ts:332-333`） | 上游注册六工具，本仓丢弃 `update`/`run_now`/`/cron`；`model-only` 是 Pi 侧"declared 但 never callable"（`docs/extensions.md:157`），上游无此概念 |
| owner/epoch 三字段 token、失效清场、同代单飞、脏标记合并 | `registerTaskSchedulerAdapter` 闭包 | 上游没有任何 session 世代/失效概念 |
| 期间事件门禁（只允许 `session_start`/`session_shutdown`） | facade `on` | 上游版本没有新增事件需求，但门禁本身必须保留 |
| 触发消息的 `PERSISTED_HEADER` + `ROUTING_CONTEXT` + `expandPromptTemplates:false` | facade `sendUserMessage` | 与版本无关 |
| `repositoryDataDir` 的仓库外/真实目录/symlink 校验 | `adapter.ts` | 上游只把 `dataDir` 当字符串拼接 |
| observer 的字段级校验、pending/running/success 语义不升级、`detail()` 只经受控 get | observer 实现 | 上游 `formatTaskSummary` 语义未变，但"观察成功 ≠ 跨 Host 最新"这一边界仍靠本仓表达 |

**并且升级会新增一个必须由用户裁决的产品语义**（这才是真实成本的主体）：`details`/`structuredContent` 是否被接受为合法上游结果形态。任何"接受后清空"的做法都被既有合同明确禁止（`docs/architecture/task-scheduler-adapter-contract.md`：「拒绝……不是接受后清空 `details`」），因此这不是实现选择，而是合同修订。
