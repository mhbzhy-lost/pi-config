# Pi 1.3.0 fullscreen 下 overlay 滚轮失效（滚轮改走 mouse 事件，本仓仍只解析 raw SGR）

## 现象

升级到 Pi 1.3.0（`@earendil-works/pi-tui` 1.3.0）后，默认全屏模式（`tuiMode: "fullscreen"`）下两个 overlay 的滚轮完全不生效：

- subagent transcript overlay（唯一 Alt+O 键在 presenter 未挂载时的 standalone 语义，`footer-runtime.ts` `standaloneActivityView().openDetails → enterBrowser`）：滚轮不动；
- 后台活动详情 overlay（同一 Alt+O 键在统一 presenter 已挂载时委托的 `presenter.openDetails`）：滚轮不动。

同一 overlay 内的键盘路径全部正常：pageUp/pageDown、Home/End、↑/↓/j/k、`x`、搜索键 `q`/Esc、Esc 焦点归还、关闭后焦点回 parent、关闭后 draft 恢复。只有**滚轮**失效。

机器侧证据（隔离 checkout `/Users/leshi.zhy/pi-upgrade-1.3.0`，Pi 1.3.0 + pi-subagents 0.79.2，进程内 stub terminal）：

- `logs/recheck-ui-scheduler/05-joint-upgrade-tui.log`：`test/joint-upgrade-tui.test.mjs:62` → `AssertionError: 29 !== 30`（页滚后滚轮未生效）。
- `logs/recheck-ui-scheduler/06-custom-footer-fullscreen.integration.log`：`test/custom-footer-fullscreen.integration.test.mjs:51` → 滚轮后 `position()` 与滚轮前完全相同（`{start:19,end:24,total:30,autoFollow:false}`）。
- 分析报告：`reports/recheck-ui-scheduler-1.3.0.md` §5.2/§9.1；预警来源：`reports/local-retirement-audit.md:164`。

## 数据来源与分类

**类别 1：预期 production 数据未被正确处理。** 触发数据是合法的公开 terminal 输入，身份、时间、资源事实全部有效，与测试 fixture 污染无关：

- 实际入口：`publicTerminal`（终端写入的 SGR 滚轮序列 `\x1b[<65;10;5M`）→ `@earendil-works/pi-tui` 1.3.0 `TuiAltScreen`；
- 权威事实：Pi 1.3.0 默认 `tuiMode: "fullscreen"`（`node_modules/@earendil-works/pi-coding-agent/dist/core/settings-defaults.js:61`），即默认宿主就是 `TuiAltScreen`；
- 差异点：1.3.0 把滚轮在 renderer 层归一化为 mouse `wheel` 事件，只调用 overlay 组件的 `handleMouse`；本仓两个 overlay 组件没有 `handleMouse`，滚轮分支写在 `handleInput`/`onInput` 里，因此成为死路径。

排除项：不是 flaky（两次运行 exit 1 结果一致，`05`/`05b`）；不是超时；不是断言放宽；不是 fixture 造假（滚轮串就是真实终端序列，page/search/焦点断言在同一文件同一 harness 下通过）；两个 overlay 的 raw 行/`tool result`/session 数据完全未被改写（`docs/bugs` 与根目录 TUI 精简边界一致：只在 renderer 层滚动投影）。

## 首个偏离点

`node_modules/@earendil-works/pi-tui/dist/tui-alt-screen.js:504-517`（`handleViewportInput`）：

```js
const wheelEvent = this.parseWheelEvent(data);
if (wheelEvent) {
    const lines = this.wheelScroll.next(wheelEvent.direction, performance.now());
    const wheelDelta = wheelEvent.direction * ((wheelEvent.button & 8) !== 0 ? lines * ALT_WHEEL_SCROLL_MULTIPLIER : lines);
    const event = this.createMouseEvent("wheel", wheelEvent.button, wheelEvent.x, wheelEvent.y, { wheelDelta });
    const overlay = this.dispatchMouseToOverlay(event);
    const result = overlay.result ?? (overlay.hit ? undefined : this.dispatchMouseToLayout(event));
    if (result) {
        if (this.applyMouseDispatchResult(event, result))
            this.requestRender();
        return { consume: true };
    }
    this.routeWheel(wheelEvent, wheelDelta);
    return { consume: true };
}
```

要点：

1. SGR 滚轮**先**被判为 wheel 事件，`return { consume: true }`，raw 输入串不再下传；
2. overlay 成分发只经 `dispatchMouseToOverlay`（`dist/tui.js:517-541`）→ `dispatchMouseEvent`（`dist/tui.js:13-38`），后者**只**调用组件 `handleMouse`，从不调用 `handleInput`；
3. 组件没有 `handleMouse`（或返回 `undefined`）时，滚轮落到 `routeWheel`（`dist/tui-alt-screen.js:796-810`），只滚 `currentLayout` 的 ScrollView 与 primary ScrollView，即底层 transcript；
4. 键盘仍走「overlay 聚焦时把 raw 输入交给 overlay」（`dist/tui-alt-screen.js:466-468` `shouldDeferViewportInputToOverlay`），所以键位一切正常——这正是「只有滚轮坏」的原因。

## 最小修复

只在两个 overlay 组件上补齐公开 `Component.handleMouse` 入口，并让 presenter 转发；不改 Host/upstream 包，不改 raw 消息/`tool result`/session 数据，不改滚动、渲染与 notify 机制：

1. `packages/pi-subagents-enhanced/src/tui/session-viewport.ts`
   - `SubagentTranscriptViewport` 新增 `handleMouse(event: TuiMouseEvent): TuiMouseEventResult | undefined`；
   - 仅处理 `event.type === "wheel"`：取公开字段 `event.wheelDelta`（1.3.0 由 `createMouseEvent` 写入，默认 `wheelScrollLines=1` 时一个物理刻度 = ±1 行），`Math.trunc` 成整数行后在 `lines === 0` 时返回 `undefined`（不消费、不滚动）；
   - 有增量时调用**既有** `scrollLines(delta)`（沿用原有 `maxStart` 钳制与 `autoFollow` 语义），返回 `{ handled: true }` 阻止渲染器再把同一滚轮交给底层 primary ScrollView（避免「双滚」）；
   - 非 wheel 事件一律返回 `undefined`，不消费不属于 overlay 正文滚动的鼠标事件（点击/拖拽/选择仍按上游默认行为）。
   - `handleInput` 与 `parseSgrWheelDirection` 原样保留：regular 模式（`TuiMainScreen`）官方确实把滚轮当 raw SGR 交给 `handleInput`，该路径仍有效且不会被 mouse 路径重复触发（1.3.0 `TuiMainScreen` 无任何 mouse 分发）。
2. `src/background-activity/detail-controller.ts`
   - `ActivityDetailShell` 接口新增 `handleMouse`；`ActivityDetailShellController` 实现同语义：`mounted` 且 `type === "wheel"` 时按 `wheelDelta` 调既有私有 `scrollLines(lines)` 并返回 `{ handled: true }`，其余返回 `undefined`；
   - `handleInput` 内既有 `parseSgrWheelDirection` 分支保留（MainScreen/regular 路径）。
3. `src/background-activity/presenter.ts`
   - `createOpenShellComponent` 的返回类型与实现各加一个 `handleMouse` 成员，仅转发 `shell.handleMouse(event)`（不复制滚动逻辑、不经手 raw 行）。
4. `packages/pi-subagents-enhanced/src/tui/footer-runtime.ts`
   - **未修改**：overlay 组件就是 `SubagentTranscriptViewport`，入口合并到组件后无需在此新增分支；`onInput` 里的 raw SGR 分支继续服务 `TuiMainScreen`。

未新增共享 utils/package，未新增 test/fixture，未把 overlay 强改为 MainScreen，未放宽任何滚动断言，未引入任何版本判断/fallback。

## 测试 harness 的必要迁移（只迁移调用，不放宽断言）

两条既有用例把滚轮串直接喂给 stub terminal，断言原样保留（`joint-upgrade-tui.test.mjs:65` 仍为 `start === page.start + 1`；`custom-footer-fullscreen.integration.test.mjs:53` 仍为 `notDeepEqual`）。1.3.0 的 `dispatchMouseToOverlay` 只在**已渲染出 overlay 几何**（`dist/tui.js:959-989` `compositeOverlays` 写入 `renderedOverlayLayouts`）时才命中 overlay；宿主是持续渲染的，输入前必有帧，而两用例在此之前从未产出帧（`requestRender()` 走 `process.nextTick`，同步断言前不会执行）。因此各自补一次公开的 `tui.renderNow()`（`custom-footer-fullscreen` 中替换原先的手工 `viewport.render(80)`），使滚轮走真实生产 `handleMouse` 协议。

## 残余风险

- 详情 overlay 仍无 fullscreen 机器覆盖（`reports/recheck-ui-scheduler-1.3.0.md` §7.3）：`presenter.openDetails` 的滚轮修复目前只有代码级判读 + 类型约束，无 `TuiAltScreen` 用例；按本任务合同不新增用例。
- 滚轮命中的前提是 overlay 已渲染出几何，且指针落在 `renderedOverlayLayouts` 的 bounds 内（详情正文短于 overlay 区域时，指针在正文之外不会滚动）；这是上游 overlay 分发语义，不是本仓可改的。
- `wheelDelta` 的量级由上游决定（默认 1 行/刻度；`wheelScrollLines: "auto"` 时最多 6 行/事件），本仓不再自行解析方向；若上游改成不带 `wheelDelta` 的 wheel 事件，`handleMouse` 会返回 `undefined` 并 fail-visible（滚轮回到「只滚底层」的旧行为），需要按新版公开类型重新核对，而不是加方向 fallback。
- `Math.trunc` 只做整数行归一（滚动 API 以行为单位）；非整数的自造事件不会被猜成方向。
