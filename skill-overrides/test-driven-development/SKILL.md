# 按授权范围参考 TDD

本 Skill 提供可选测试方法，不是生产代码、配置或 Skill 修改的默认前置条件。未经用户明确授权不得主动编写测试，不要求先有失败测试才能修改实现，也不要求删除已有代码重做流程。

## 何时使用

用户明确要求某项功能采用 TDD 时，可在该具体范围使用 RED → GREEN → REFACTOR。用户仅要求实现功能、修复 bug、编写计划、运行已有检查或修改 Skill，不自动构成测试编写授权。

用户只授权补充测试时，按实际需求选择测试顺序，不将测试授权扩大为所有后续需求的持续授权。

## 可选方法

在已记录 **已授权（功能与测试范围）** 后：

1. 从合法公开入口和预期产品行为选取场景，避免直接拼不可达状态。
2. 编写获准的行为检查，记录实际失败及其原因；已有实现满足行为时如实记录通过。
3. 修改最小实现，运行必要检查；失败先分类来源，不增加无证据 production fallback。
4. 必要时整理实现，保留已观察的语义与资源边界。

## 测试建议

计划可以列具体公开入口、身份、事件顺序、预期行为和资源条件，但新增测试、全新 mock/fixture 和压力场景统一标记 **建议（待用户授权）**。既有测试、断言和既有 fixture 可随已授权生产修复同步调整。

已有测试可按当前任务授权运行；它们通过不等于新增测试获准。真实 provider、网络、Host、设备或危险进程实验遵守各自资源授权。

可选参考 `writing-good-tests.md`：它描述已获准测试的质量，不是默认编写义务。交付时区分静态检查、既有测试结果、新行为验证及未运行场景。
