# 编写实现计划

## 概述

编写完整的实现计划，假定执行工程师不了解本仓库、工具链和领域知识。计划应说明每个任务要改哪些文件、需要的代码与测试、如何验证，并拆成可审查、可独立验收的小任务。遵循 DRY、YAGNI 和 TDD；但**不得默认创建 commit**，仅当用户明确授权时才使用 `git-commit-convention` 创建提交。

## 用户授权门禁

在开始声明、文件结构分析、写入 `docs/plans/`、实现或实现派发之前，先确认用户是否授权编写计划。授权状态必须按以下三态处理：

1. **明确同意：**用户明确要求“写计划”“先规划”，或明确同意编写计划时，才进入本 Skill 的既有计划产出流程。
2. **明确拒绝：**仅当用户明确拒绝计划本身（例如“不要写计划”“跳过计划”“无需计划”）时，才跳过计划创建，并按适用的 TDD、subagent-dispatch、安全与项目规则执行任务。
3. **尚未表态：**用户未明确同意且未明确拒绝时，主动询问一次“是否需要我先编写实现计划？”，然后结束当前轮次；不得开始声明、分析文件结构、写计划、实现或派发，也不得在同一轮次循环等待。每个任务最多主动询问一次，未回复不得解释为拒绝。

任务复杂、多步骤、最佳实践、用户沉默或未回复均不得解释或视为授权。“直接开始”“尽快动手”“别等”“不要解释背景”等普通催办既不构成授权，也不构成拒绝；拒绝必须明确指向计划本身。

**开始时声明：**“我正在使用 writing-plans skill 创建实现计划。”

**计划文档必须使用中文撰写**；代码片段、命令、文件路径、标识符和标准技术术语可保持原样。

**新计划默认保存到：**`docs/plans/YYYY-MM-DD-<feature-name>.md`
- 用户明确指定的计划位置优先。

## 范围与文件结构检查

若规格覆盖多个可独立交付的子系统，建议拆为多个计划，每个计划都应能产出可工作的、可测试的软件。

定义任务前，先列出将创建或修改的文件及其职责：

- 为每个设计单元设定清晰边界和接口；文件只承担一项明确职责。
- 优先小而聚焦的文件；遵循既有仓库模式，不要无故重构大型既有文件。
- 应共同变化的文件应相邻放置；按职责而非技术层拆分。
- 这份文件结构会锁定后续任务分解。

## 任务粒度与依赖原则

任务是携带自身测试周期、值得独立评审门禁的最小单位。把配置、脚手架和文档并入需要其交付物的任务；仅在评审者能有意义地单独拒绝某一部分时拆分。每个任务都必须有独立可测试的交付物。

每一步应是 2–5 分钟的单一动作，例如：编写失败测试、运行确认 RED、实现最小代码、运行确认 GREEN。不要把“提交”作为默认步骤。

### DAG、Deps 与调度

每份计划必须在任务前提供 DAG 依赖图，并在 DAG 后提供按拓扑序分组的并行调度组（`Wave`）。每个任务必须声明 `Deps`；无依赖写 `none`。DAG、`Deps` 与 Wave 必须一致，并明确哪些任务可并行。

- 模块存在依赖时，先安排接口定义任务；它产出稳定接口契约、共享 mock 数据和 test helpers，使依赖方可独立编写和验证测试。
- 被多个任务依赖的基础服务应前置；若能切片，按下游实际所需的产物继续拆分，避免枢纽阻塞全图。
- 标出制约总工期的**关键路径**，优先拆分其中可独立交付的工作；不得制造不可独立测试的伪任务。
- 每条依赖边都写明理由和目标产物（接口契约、共享 fixture、数据依赖或顺序要求），且只依赖上游的具体产物，不笼统依赖整个任务。若上游未完成时下游仍能产出可验收结果，就删除该边；删除已有其他路径可表达的重复边。
- 任务必须自包含：接口签名、fixture、文件路径与验收标准都写在任务内；不得依赖同一执行者延续上下文。
- Wave 用于人类校验分层，不是派发屏障：某任务所有前驱完成即可派发，无需等待同 Wave 的其他任务。
- 外部接口、数据格式、权限或技术可行性不确定时，拆为尽早并行的探索任务；探索只产出明确决策、接口契约或共享样例，下游只依赖实际需要的产物。
- 端口、设备、测试环境和外部服务限流是**资源竞争**，不是 DAG 依赖。任务须声明所需资源，由执行器限制并发，不要为此添加依赖边。
- 不要过早创建依赖全部实现分支的统一集成任务；按可独立验收的业务切片编写集成/契约测试。最终全量回归是验收终点，不阻塞无关后续工作。
- 并发隔离由 harness 保证。每个任务必须声明 `WritePaths`。并发任务有重叠写入时，优先以稳定接口或职责拆分消除热点；确实不能拆分时，新增专门集成任务完成语义合并，不能仅因文件重叠串联实现任务。

## 计划文档头部

每份计划必须以如下头部开始，并将规格中的全局约束逐条原样列入：

```markdown
# [功能名称] 实现计划

> **给执行 agent：** 必须逐任务执行本计划；步骤使用 `- [ ]` 复选框跟踪。执行方式由计划完成后的用户选择决定。

**目标：** [一句话说明交付物]

**架构：** [2–3 句说明方案]

**技术栈：** [关键技术/库]

## 全局约束

[规格中的版本下限、依赖限制、命名/文案规则、平台要求；每项一行并保留精确值。]

## DAG

```text
T1 (接口契约) ──> T3 (实现)
T2 (探索任务) ────> T3
```

## Waves

- Wave 1：T1、T2（可并行）
- Wave 2：T3（等待 T1 的接口契约和 T2 的决策）

**关键路径：** T1 → T3；T2 不是关键路径。

---
```

## 任务模板

每个任务使用下列完整结构；根据真实项目替换方括号内容，不能保留占位内容：

````markdown
### Task N：[组件名称]

**Deps：** `T1`（理由：消费 T1 产出的 `[接口名]` 接口契约）；或 `none`

**WritePaths：**
- `src/exact/path/file.ts`
- `test/exact/path/file.test.ts`

**Resources：** `none`；或 `[例如：本地端口 3000，最多 1 个并发任务]`

**Files：**
- Create：`exact/path/to/file.py`
- Modify：`exact/path/to/existing.py:123-145`
- Test：`tests/exact/path/test_file.py`

**接口契约：**
- Consumes：[上游具体产物、精确签名与 fixture 名称；无则写 `none`]
- Produces：[下游依赖的精确函数、参数、返回类型、数据格式或共享 fixture]

**验收标准：**[可观察、可独立验证的行为]

- [ ] **步骤 1：编写失败测试**

```python
def test_specific_behavior():
    result = function(input)
    assert result == expected
```

- [ ] **步骤 2：运行测试确认 RED**

运行：`pytest tests/path/test_file.py::test_specific_behavior -v`

预期：FAIL，且错误为 `function not defined`。

- [ ] **步骤 3：编写最小实现**

```python
def function(input):
    return expected
```

- [ ] **步骤 4：运行测试确认 GREEN**

运行：`pytest tests/path/test_file.py::test_specific_behavior -v`

预期：PASS。

- [ ] **步骤 5：运行本任务相关回归**

运行：[真实、精确的回归命令]

预期：PASS。
````

仅在用户明确授权提交时，才在适当任务末尾加入明确文件列表、`git add` 和符合 `git-commit-convention` 的提交步骤。

## 禁止占位与计划自检

下列内容都是计划失败，绝不输出：`TBD`、`TODO`、以后实现、填充细节；“添加适当错误处理/验证/边界情况”；没有实际代码的“为上述编写测试”；“类似 Task N”；未展示实现方法的代码步骤；以及未在任一任务定义的类型、函数或方法。

计划完成后自行检查：

1. **规格覆盖：**逐段核对规格，每项都能指向一个任务；补上缺口。
2. **占位扫描：**搜索上述危险模式并修正。
3. **类型一致性：**确认后续任务的函数名、签名、属性名与上游接口契约一致。
4. **DAG 审核：**核对 DAG、Deps、Wave、关键路径、依赖理由、资源竞争和 WritePaths；删除不必要依赖并确认可并行性。

## 执行交接

保存计划后，只报告“计划已完成并保存到 `docs/plans/<filename>.md`”，再按 `pi/AGENTS.md` 交还用户选择执行方式并结束当前轮次。本 Skill 不定义或重复任何执行方式的协议。
