# 获授权后的 Skill 评估参考

本文件描述可选的 Skill 使用评估方法，改编自 Superpowers writing-skills 的测试方法。**它不要求默认运行 subagent、fresh-context 压力场景或先写失败测试。** 只有用户明确授权具体评估范围后，才可执行相应场景，并在记录中写明「已授权（范围）」。

「压力测试」「TDD」「RED/GREEN」「fresh-context」「micro-test」都是可选方法名，不能作为 Skill 编写、修改或普通 coding task 的默认门禁。

## 评估前

- 明确要观察的行为、版本、输入、资源和停止条件。
- 记录 Skill 的触发条件和预期输出形状。
- 未授权时只做静态阅读、路径核对和已有检查，不能把建议写成已执行。

## 何时值得评估（获授权后）

适合评估的 skill：强制纪律、有遵守成本（时间/精力/返工）、可能被合理化绕过（"就这一次"）、与即时目标冲突（速度优先于质量）。纯参考类 skill（API 文档、语法指南）通常只需检索/应用场景，不需压力场景。

## TDD 映射（可选方法）

| TDD 阶段 | Skill 评估 | 做什么 |
|---|---|---|
| RED | 基线 | 无 skill 跑场景，观察 agent 失败 |
| 验证 RED | 捕获合理化 | 逐字记录失败 |
| GREEN | 写 skill | 针对具体基线失败 |
| 验证 GREEN | 压力复核 | 有 skill 跑场景，确认遵守 |
| REFACTOR | 堵漏 | 找新合理化，加对策 |
| 保持 GREEN | 再复核 | 重测，确保仍遵守 |

## 获授权后的可选步骤

1. 用与实际使用相同的上下文运行公开入口。
2. 记录实际选择、输出、偏离点和完整事件顺序。
3. 若需对照，分别说明是否加载 Skill；不要把单次样本外推成稳定行为。
4. 根据已观察缺口修改 Skill，再执行用户授权范围内的复核。
5. 记录未覆盖的 provider、Host、网络、凭据、并发和压力条件。

### 压力场景编写（若授权压力评估）

- 具体选项：强制 A/B/C 选择，而非开放问答。
- 真实约束：具体时间、真实后果、真实文件路径。
- 让 agent 行动："你会怎么做"，而非"应该怎么做"。
- 组合 3+ 压力更有效。压力类型：时间、沉没成本、权威、经济、疲惫、社交、务实。

### 措辞 micro-test（若授权措辞评估）

全量压力场景慢且贵，先验证措辞本身：
1. 每次一个 fresh-context 样本；system prompt 用真实上下文（完整 skill/模板，而非孤立指导）。
2. 必带无指导对照组；对照组不出现失败就无需修。
3. 每个变体 5+ 次重复；单样本会说谎。
4. 人工读每个命中；模板回声/引用反例会冒充命中。
5. 方差是指标：指导生效时重复会收敛到同一形状。

micro-test 验证措辞，不替代纪律 skill 的压力场景。

### 堵漏与 meta-testing（若授权迭代）

- 捕获新合理化原话，加入合理化对照表与红旗清单。
- 对策要具体（"不要留作参考"有效，"别作弊"无效）。
- agent 仍选错时问它"skill 怎么写才能让你明确只选 A"，区分文档问题/组织问题/明知故犯。

## 结果记录

区分静态合同、已有检查、获授权行为验证和未执行建议。测试失败先做 provenance 分类；没有证据证明 production 可达时，不增加 fallback 或兼容分支。真实 provider、网络安装、Host/PTY、危险进程和跨进程实验分别需要相应资源授权。
